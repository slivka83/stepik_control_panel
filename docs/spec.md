## 🛑 1. КРИТИЧЕСКИЙ АРХИТЕКТУРНЫЙ ПРИОРИТЕТ: ZERO-WRITE POLICY (READ-ONLY STATE)

Приложение является исключительно аналитической BI/ERP-панелью (Business Intelligence). Любая прямая модификация данных на серверах Stepik из кода нашего приложения **категорически запрещена**.

1. **HTTP-методы:** Использовать только HTTP-метод `GET` при интеграции со сторонним API Stepik. Методы `POST`, `PUT`, `PATCH`, `DELETE` для внешних запросов к Stepik полностью исключены на уровне архитектуры.


2. **OAuth2 Scopes:** При инициализации сессии авторизации запрашивать у Stepik токены строго с правами уровня `read`. Права уровня `write` запрашивать запрещено.


3. **Изоляция действий (Deep Links):** Все интерактивные действия (баны, ответы, редактирование дедлайнов, выдача промокодов) должны осуществляться путем генерации **прямых глубоких ссылок (Deep Links)** на оригинальный интерфейс Stepik, открываемых в новой вкладке браузера (`target="_blank"`). Приложение подсвечивает проблему, но отправляет пользователя решать её на базовый сайт.

## 4. ПОШАГОВЫЙ ПЛАН РЕАЛИЗАЦИИ BACKEND (FASTAPI)

### Шаг 4.1. Авторизация OAuth2 и шифрование токенов

1. Создать роут `GET /api/auth/login`, перенаправляющий на OAuth-сервер Stepik с параметрами `response_type=code`, `client_id` и `scope=read`.


2. Создать роут `GET /api/auth/callback`. При получении `code` сделать асинхронный запрос к Stepik для обмена кода на `access_token` и `refresh_token`.


3. Использовать библиотеку `cryptography.fernet` для шифрования токенов перед записью в базу данных `users`. Ключ шифрования `ENCRYPTION_KEY` считывать из файла `.env`.



### Шаг 4.2. Механизм отказоустойчивости API: Token Bucket и Ошибка 429 (NFR 1)

1. Реализовать middleware или декоратор для исходящих запросов к Stepik с использованием Redis.
2. Приложение должно отслеживать Rate Limits. В случае получения HTTP-статуса `429 Too Many Requests` извлечь заголовок `Retry-After`.


3. Программа должна автоматически приостановить выполнение текущего потока синхронизации через `await asyncio.sleep(retry_after)`. Прерывать сессию пользователя запрещено — фронтенду возвращается статус `202 Accepted` с текущим прогрессом.


4. Использовать пакетную загрузку параметров (Side-loading) через передачу массива идентификаторов: `?ids[]=1&ids[]=2` для оптимизации количества запросов.



### Шаг 4.3. Асинхронные бизнес-метрики и Smart Analytics

1. **Расчет Сегментов Когорт (BR 1):** Написать SQL-скрипт, распределяющий записи в `student_enrollments` на основе разницы между `current_date` и `last_viewed_at`:


* $\le 7$ дней $\rightarrow$ `Active`

* $8 - 30$ дней $\rightarrow$ `Passive`

* $30 - 90$ дней $\rightarrow$ `Fading`

* $> 90$ дней $\rightarrow$ `Sleeping`



2. **Predictive Churn (FR 4.6):** На основе логов попыток решений (`Attempt_Analytics`), если у студента из категории `Active` доля ошибок `time_limit_exceeded` или `memory_limit_exceeded` за последние 5 попыток превышает 15%, а интервал между заходами увеличился в 2 раза — выставлять флаг `churn_risk = True`.


3. **AI-Дайджест (Smart Daily Insights) (FR 2.3):** Интегрировать библиотеку `openai` / `anthropic`. Раз в сутки по cron собирать агрегированные показатели: сумму Net Revenue, количество оформленных возвратов за день, количество B2B инвайтов. Отправлять структурированный JSON в LLM и сохранять сгенерированный текст в базу для выдачи на фронтенд.


4. **Market Basket Analysis (FR 3.5):** Написать SQL-запрос для построения матрицы совместных покупок. Посчитать пересечение `course_id` у уникальных `student_id`. Если поддержка связи $> 0.2$ (например, 80% купивших курс по SQL покупают курс по Python), отдавать эту связку в эндпоинте `/api/analytics/cross-sell`.

## 6. СПЕЦИФИКАЦИЯ ВНЕШНЕЙ ИНТЕГРАЦИИ (STEPIK API PARSING)

Для наполнения локальной БД использовать исключительно HTTP `GET`-запросы к следующим эндпоинтам Stepik:

1. `GET /api/courses/{id}` — получение первичных метаданных курса, статуса публикации, названия и связей.


2. `GET /api/sections?course={course_id}` и `GET /api/units?section={section_id}` — парсинг структуры курса и актуального расписания дедлайнов.


3. `GET /api/steps?lesson={lesson_id}` — выгрузка содержимого шагов для текстового парсинга, поиска битых ссылок и кэширования контента (`content_cache`).


4. `GET /api/course-grades?course={course_id}` — выгрузка ведомости оценок студентов для сверки прогресса и работы триггеров алертов по сертификатам.


5. `GET /api/submissions?course={course_id}&status=wrong` — сбор аналитики по неудачным попыткам для выявления технических сбоев (`time_limit_exceeded`).

## 7. КРИТЕРИИ ПРИЕМКИ (ACCEPTANCE CRITERIA)

1. **Отсутствие мутирующих запросов:** В коде всего проекта (и фронтенд, и бэкенд) нет ни одного упоминания `requests.post`, `axios.put` или эквивалентных методов, направленных на домен `stepik.org`.


2. **Скорость работы UI (NFR 2):** Первичный рендеринг главного дашборда на базе кэшированных данных PostgreSQL занимает не более 2 секунд для курсов с базой до 100 000 студентов.


3. **Корректность обработки Rate Limit:** При симуляции ответа 429 от API Stepik скрипт синхронизации бэкенда засыпает на время, указанное в `Retry-After`, не прерывая выполнение общего цикла и сохраняя стабильность сессии.


4. **Безопасность учетных данных (NFR 4):** Ни один секретный ключ, пароль от БД или Client Secret от OAuth API не захардкожен в кодовой базе. Все конфигурации считываются строго из переменных окружения `.env`.
